# Week 02 Day 03 - DBMS in Modern Services

## 학습 목표

- MySQL, PostgreSQL, Redis, Milvus의 역할을 서비스 관점에서 비교한다.
- 원본 데이터, 캐시, 이벤트 로그와 검색 인덱스를 분리한다.
- 하나의 API에서 여러 저장소를 조합하는 흐름을 이해한다.
- 공간 길찾기에서 DBMS별 책임을 구분한다.

## DBMS별 책임

| DBMS | 데이터 모델 | 강점 | 대표 용도 |
| --- | --- | --- | --- |
| MySQL | 관계형 테이블 | 단순한 거래 처리와 JOIN | 주문, 결제, 재고, 회원 |
| PostgreSQL | 관계형 + JSONB + 확장 | 복잡한 SQL, 분석, 지리 정보 | 운영 DB, 이벤트 분석, 공간 데이터 |
| Redis | Key-Value, Hash, Stream | 매우 빠른 읽기와 짧은 상태 관리 | 캐시, 세션, 랭킹, 요청 제한 |
| Milvus | Embedding Vector + Metadata | 의미 기반 유사도 검색 | RAG, 추천, 이미지 검색 |

중요한 기준은 제품 이름이 아니라 데이터에 필요한 책임이다. 돈, 재고, 권한처럼 틀리면 안 되는 원본은 관계형 DBMS에 두고, 반복 조회는 Redis, 의미 검색은 Milvus가 담당한다.

## 서비스 조합 예시

```text
사용자 요청
  -> MySQL/PostgreSQL: 정합성이 필요한 원본 읽기와 쓰기
  -> Redis: 캐시, 세션, 실시간 상태 확인
  -> Milvus: 의미가 비슷한 후보 검색
  -> PostgreSQL: 운영 이벤트와 분석 로그 기록
```

### MySQL

회원, 주문, 주문 상품, 상품, 결제를 키로 연결한다. 주문 상세 화면은 주문을 기준으로 고객, 상품과 결제를 붙이며, 결제 정보가 아직 없을 수 있으면 `LEFT JOIN`을 사용한다.

### PostgreSQL과 JSONB

공통 분석 축은 정형 컬럼에 두고, 화면과 이벤트마다 달라지는 속성은 JSONB에 저장한다. GIN 인덱스는 JSONB 내부 키와 값을 빠르게 찾는 데 사용한다.

### Redis

Cache-aside 패턴에서는 Redis를 먼저 조회하고 값이 없을 때 원본 DB를 읽은 뒤 TTL과 함께 캐시에 저장한다. 세션과 요청 제한처럼 짧은 상태는 `SETEX`, `INCR`, `EXPIRE` 등을 활용할 수 있다. Redis는 영구 원장보다 빠른 상태판으로 취급해야 한다.

### Milvus

문장, 이미지 또는 위치 특징을 Embedding으로 변환하고 가까운 벡터를 Top-K로 검색한다. Milvus에는 벡터와 메타데이터를 두고, 실제 원문은 관계형 DB나 Object Storage에서 가져오는 구조가 적합하다.

## 길찾기 서비스의 역할 분리

건물 면적과 도로를 이용한 길찾기는 다음처럼 조합할 수 있다.

1. Milvus가 건물 외곽 Edge와 방향이 가까운 도로 후보를 빠르게 줄인다.
2. PostGIS가 Polygon, LineString, 거리와 교차 여부를 정확하게 검증한다.
3. pgRouting이 거리, 시간, 회전과 통행 조건을 합산해 최종 경로를 계산한다.

Milvus의 벡터 검색은 후보 탐색에 강하지만 정확한 최단 경로 계산을 대체하지 않는다.

## 운영 시 고려 사항

- 관계형 원본과 캐시 또는 검색 인덱스의 동기화 방식
- TTL, 장애와 재시작을 고려한 Redis 영속성 전략
- Milvus 결과에서 원문을 찾아오는 식별자와 메타데이터
- 백업, 모니터링, 장애 복구와 보안 정책
- DBMS별 비용과 관리 복잡도
